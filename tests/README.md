# 回帰テスト

スキルを変更したとき、変更前に抜けていなかった指摘が抜けていないか、誤検出が増えていないかを確かめる。

## 構成

- `fixtures/` — レビュー対象のコード。実プロジェクトの修正前コードと、指摘が出てはいけないコード（`clean-route`）
- `expected.json` — 各サンプルで出るべき指摘。`passes` 以外は変更しない
- `baseline.md` — 実行結果の記録
- `feedback.md` — 実際に使ったときの指摘の扱いの記録（誤検出の測定）

## 実行手順

1. サンプルごとに、新しいサブエージェントを 3 回起動する（LLM の出力はぶれるので 1 回では判断しない）
2. 各回に次を渡す：まず `SKILL.md` だけを読み、リンクされた `references/` は、対象のコードに必要だと自分で判断したものだけ読む（実際の使い方に合わせる。全部読ませるとトークンの無駄で、実使用ともずれる）。`targets` をレビューする。ファイルは編集しない。期待値（`expected.json`）は見せない。他のプロジェクトファイルは参照できないので、確認できないことは `unverified` にする。最後に、実際に読んだ references を報告させる
3. 出たレポートを `expected` と照合し、各項目が 3 回中何回出たかを数える
4. `clean-route` / `clean-test` は must / should が 1 件でも出たら、その回は失敗
5. `rereview` は `context` の前回レポートを渡し、「修正したので再レビューして」と頼む。`forbidden` の指摘が 1 件でも出たら、その回は失敗

## 判定

- 項目の `passes` は 3 回すべてで `min_severity` 以上の重要度で出たときだけ `true`
- 変更後は同じ手順をもう一度やり、基線より悪化していないかを比べる
- 通らないからといって、`expected.json` の期待値を消したり重要度を下げたりしない

## 注意

- 期待値は、同じモデルによる過去のレビューから作った。独立した正解ではない点に注意する
- サブエージェントを呼ぶので実行に費用がかかる。1 回あたりの目安は、サブエージェント全体で calc が約 12 万、chart-hook が約 13 万、clean-route が約 10 万トークン
- 変更した内容に関係するサンプルだけを実行する（全部を毎回回さない）。ただし `clean-route` と `clean-test` は誤検出の確認のため、スキル本体を変えたら必ず回す
- スキルを変えるコミットには、理由と変更内容に加えて、どう確認したか（実行したサンプルと結果）を書く
- 実際の使用で見逃しや誤検出が見つかったら、作者が確認したうえで `fixtures/` と `expected.json` に追加する。`source` が「作者の確認待ち」のサンプルは、作者の確認が済むまで合成の暫定値として扱う
- 読んだ references の記録は、`SKILL.md` の案内が効いているかを見る手がかりになる
