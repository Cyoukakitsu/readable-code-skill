# リーダブルコード・レビュー

読みやすいコードの目標は、初めて読む人が理解するまでの時間を最短にすること。ここでいう「理解」は、意味が分かるだけでなく、変更やバグ修正ができ、他のコードとの関係まで把握できる状態を指す。行数を減らすことは目標ではない。「短くする」と「理解にかかる時間を短くする」がぶつかったら、後者を選ぶ。

## モード

- レビューのみ。ファイルは編集しない。修正案は小さなコード片としてレポートに書く。
- ユーザーに修正の適用まで頼まれた場合でも、改名は先に影響範囲を数える。同じファイル内だけで完結するなら適用してよいが、他のファイルに波及するなら、適用前に件数を示して確認を取る（[references/naming.md](references/naming.md) の「改名を適用するとき」）。
- 渡されたもの（ファイル、diff、PR）だけをレビューする。指摘の直接の原因でない限り、周辺の未変更コードの書き換えは提案しない。

## 指摘する前に

- チェックや分岐が不要だと主張するには、まずそれが依存している呼び出し先・型・取り決めを読む。参照できない場合は、その指摘に `unverified` を付け、重要度を下げる。
- ESLint・Prettier・`tsc` がすでに強制していること（命名の大文字小文字規則（camelCase など）、インデント、未使用変数）は扱わない。
- lint で判定できる規則（`no-nested-ternary`、`max-depth`、`no-unused-expressions` など）は、プロジェクトの ESLint 設定で有効になっていれば指摘しない。無効なら指摘してよいが、同じ種類の違反は 1 件にまとめて該当箇所を列挙し、レポートの末尾でルールを有効にすることを 1 行だけ提案する（設定ファイルは編集しない）。設定ファイルを確認できなければ、有効かどうか分からない旨を添えて指摘してよい。
- 見た目の整形（空白、改行位置、波括弧の位置、縦の位置揃え）は、フォーマッタの設定がなくても指摘しない。必要なのは個別の指摘ではなくフォーマッタの導入であり、気になるならレポートの末尾で 1 行だけそう書く。縦の位置揃えは Prettier に消され、差分も汚すので、勧めもしない。
- 例外として、フォーマッタが扱えない「並び順」の不統一は `optional` で指摘してよい。同じフィールド群が、型定義・関数の引数・オブジェクトの組み立てで別々の順序になっている場合など。
- プロジェクトの既存の慣習に従う。指摘するのはコードベース内の不統一であって、自分の好みとの違いではない。

## チェック項目

references は全部は読まない。**どのレビューでも読む**のは次の 3 つ（指摘の多くがここから出る）: `naming.md`、`comments.md`、`compression.md`。残りは、対象に該当するコードがあるときだけ読む。

- `control-flow.md` — 入れ子の `if`、三項演算子、コールバックの連なりがある
- `variables.md` — `let`・再代入、モジュールスコープの値、`useEffect` / `useMemo` の依存配列がある
- `defensive-code.md` — `try/catch`、null チェック、入力の検証、保険のような分岐がある
- `extraction.md` — おおむね 30 行を超える関数・`useEffect` がある、数式・正規表現・日付や文字列の加工・ブラウザ API の生の操作・大きな設定オブジェクトが業務の流れに挟まっている、または 1、2 行の補助関数が何段も呼び合っている
- `single-task.md` — 1 つのループ・式・分岐の中で、絞り込み・変換・検証・集計・判定・副作用のうち 3 種類以上が同時に進んでいる
- `explain-first.md` — おおむね 30 行を超える関数・`useEffect`・Route Handler がある（流れを自分で説明してコードと比べる）。設計や要件の資料がレビュー対象に含まれている場合も読む
- `less-code.md` — 省略可能な引数や `options` オブジェクト、`interface`・抽象クラス・ファクトリ・ジェネリクス、設定フラグによる分岐、自前のキャッシュ、コメントアウトされたコードがある

1. **防御コード** — 起こりえない状況のための分岐。[references/defensive-code.md](references/defensive-code.md) を参照。
2. **命名** — 中身が何か、呼び出しコストがどれくらいかが読み取れない名前、別の意味に取れる名前、中身と食い違う名前。[references/naming.md](references/naming.md) を参照。
3. **巨大な式と詰め込み** — 一度に読めない長い式、短いが読み手が頭の中で展開しなければならないコード、意図の隠れた短絡評価。[references/compression.md](references/compression.md) を参照。
4. **コメント** — コードと食い違うコメント（テストの説明文を含む）、書かれていない「なぜ」、コードの言い換えにすぎないコメント。[references/comments.md](references/comments.md) を参照。
5. **制御フロー** — 深いネスト、状態をつないだ三項演算子、追いにくいコールバック。プロジェクトの ESLint で有効になっている規則は lint に任せる。[references/control-flow.md](references/control-flow.md) を参照。
6. **変数** — 情報を足さない変数、制御フラグ、必要以上に広いスコープ（特にリクエストやインスタンスをまたいで共有されるモジュールスコープの値）、段階ごとに意味が変わる再代入。[references/variables.md](references/variables.md) を参照。
7. **下位問題の抽出** — 関数の目的と関係のない処理が場所を取っているもの、標準 API や既存のユーティリティで済むのに手書きしているもの、呼び出しをたどる手間だけを増やす薄い関数。[references/extraction.md](references/extraction.md) を参照。
8. **一度に一つのこと** — 同じループ・式の中で、絞り込み・変換・検証・集計・判定・副作用が同時に進んでいるもの。まず段落に分けることを考える。[references/single-task.md](references/single-task.md) を参照。
9. **説明と構造の対応** — 関数の流れを自分で 3〜5 ステップに説明し、コードの並びと比べたときのずれ（説明に出てこない処理、順序の違い、ステップの混在、長い関数でメインの流れが見えない）。[references/explain-first.md](references/explain-first.md) を参照。
10. **書かなくていいコード** — 今の要件にない先回りの実装（誰も渡していない引数・オプション、実装が 1 つしかない抽象化、計測していない性能対策）と、使われなくなった残骸（コメントアウトされたコード、呼び出し元のない関数）。「使われていない」と言う前に呼び出し元を検索する。[references/less-code.md](references/less-code.md) を参照。

## 出力する前に

10 の観点それぞれについて、「該当するコードがなかった」のか「見たが指摘がなかった」のかを確認する。読まなかった reference がある場合は、そのファイルが扱う種類のコード（上の一覧）が対象に本当にないかを確かめる。確認のためだけにレポートを長くしない。

## 出力形式

レポートはユーザーの言語で書く。指摘ごとに次の形式を使う。

```
### [must | should | optional] path/to/file.ts:行番号 — 短いタイトル
- 問題: ここで何が読みにくいか
- 理由: 読み手の時間をどう奪うか、どう誤解させるか
- 修正案: 小さなコード片、または改名案
- 影響範囲: 改名・削除で変更が必要になる呼び出し元やファイル（あれば）
- （unverified: 確認できなかったこと）
```

- `must`: 読み手を誤解させる、または実際のバグを隠しうる。`should`: 読むのが明らかに遅くなる。`optional`: 細かい改善。
- 同じ行範囲に複数の観点（防御コード・命名・式・コメント・制御フロー・変数・抽出・一度に一つのこと・説明と構造・書かなくていいコード）の問題があれば、必ず 1 件にまとめ、観点を併記する。
- 同じ箇所の複数の問題を 1 件にまとめるときは、含まれる問題のうち最も重い重要度を付ける。たとえば「不要な防御」（`should`）と「コメントとコードの食い違い」（`must`）をまとめたら `must`。軽いほうの分類に引きずられて重要度を下げない。
- 重要度順に並べる。指摘は最大 10 件程度。それ以上ある場合は上位だけを報告し、省略した件数を書く。
- 大きな問題がなければ、その旨を率直に書く。レポートを埋めるために指摘をでっち上げない。指摘がなければ次の程度の短さでよい。

```
重要度 must / should の指摘はありません。気になる点は optional が 1 件だけです。
- optional path/to/file.ts:12 — 〇〇（理由は一文、修正しなくても支障はない）
```

## 注意点（Gotchas）

- 「念のため」の防御分岐を追加するよう勧めない。過剰な防御は、このスキルが見つけるべき主要な問題の一つであり、AI が生成したコードでは特に起きやすい。
- 信頼境界（ユーザー入力、外部 API のレスポンス、LLM の出力、環境変数、Webhook のペイロード、ファイルの内容（`JSON.parse` の結果を含む））での防御は指摘しない。
- 悪い名前を補うためのコメント追加を提案しない。改名を提案する。
- 「なぜ」が欠けているコメントを指摘するとき、理由を推測して書き込まない。理由は作者にしか分からず、もっともらしい推測は間違っていても正しく見える。修正案は空欄にして作者に委ねる。
- 食い違いの原因が業務上の意図（仕様）にかかわり、コードとコメントのどちらが正しいかをコードからは決められない場合、片方に決めつけない。両方の可能性と、判断の手がかり（テスト、呼び出し元、仕様書）を書き、作者に確認するよう促す。作者が確認できるまでは、コードの動作を変える修正案は出さず、コメントやテスト名の修正にとどめる。
- 可読性の範囲を超えていても、バグや無駄な再実行を隠している問題（毎回新しい配列が `useEffect` の依存に入っていて、重い処理が毎レンダリング走る、など）は、見つけたら `must` / `should` で報告する。可読性の問題ではないことを一言添える。
- 名前もコメントも、それだけを見て評価しない。必ず中身のコードと突き合わせる。もっともらしいのに中身と食い違っているものが、いちばん見逃されやすく、いちばん重い。
- フレームワークが要求する名前は指摘しない（React の `useX` フック、TypeScript の `get` アクセサの構文、NestJS/Next.js の慣習）。ただしアクセサの中で重い処理をしている場合は、構文ではなく中身の問題として指摘する（[references/naming.md](references/naming.md)）。
