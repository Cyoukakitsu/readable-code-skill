# 一度に一つのこと

原則: 一つのコードのかたまり（ループ、関数、式）は、一度に一つのタスクだけを扱う。絞り込み、変換、検証、集計、判定が同じかたまりの中で同時に進んでいると、読み手は複数の目的を同時に覚えながら読むことになる。分けるときの最初の一歩は、関数への切り出しではなく「段落」にすること。タスクごとに区切り、一つ終えてから次へ進む順序にする。（第 11 章）

[extraction.md](extraction.md) との分担: あちらは、関数の目的と関係のない下位問題（数式、正規表現、日付の加工、生の API 操作、大きな設定）を関数の外へ出す話。こちらは、同じかたまりの中で複数のタスクが絡み合っている話。同じ行範囲で重なったら 1 件にまとめ、修正案は軽いほう（段落に分ける）から出す。

## 見つけ方

次のうち 3 種類以上が、同じループ・式・分岐の中で同時に進んでいたら指摘する（`should`）。2 種類なら `optional`。

- 絞り込み（対象を選ぶ）
- 変換・整形（値の形を変える）
- 検証・除外（空や不正な値を捨てる）
- 集計・計算
- 判定（最終的な真偽や区分を決める）
- 副作用（送信、保存、画面の更新）

目安は、「このかたまりは何をしているか」に、「〜して、〜して、〜する」と接続詞でつなぐ以外に答えられないこと。

修正案は次の順に検討する。

1. 段落に分ける。タスクごとに空行で区切り、途中の結果に名前を付ける。動作が変わらないので最初に検討する
2. 処理の連鎖に分ける（`filter` → `map` など）。下の「分けるときの落とし穴」を確かめてから出す
3. 単独で検証する価値がある、または再利用される段落だけを関数に切り出す（[extraction.md](extraction.md)）

### 値の取り出しと書式の連結を 1 行に詰めている

入れ子のオブジェクトからの取り出し、空の判定（既定値の補完）、書式の変換、文字列の連結が一つの式やテンプレートリテラルに入っているものは、「取り出して既定値を補う」と「連結する」の 2 段に分ける（`should`）。階層が深いほど効く。取り出しや検証が複数の場所で同じなら、補助関数にする。

## 分けるときの落とし穴（動作が変わる）

- **`||` と `??` を一緒に直さない**: 分けるついでに `||` を `??` に書き換えると、空文字が既定値に置き換わらなくなる（`"" || "未設定"` は `"未設定"`、`"" ?? "未設定"` は `""`）。空文字が来うるなら `||` のままにする。判断は [compression.md](compression.md) の `||` の項に従う。
- **絞り込みと変換を別のステップにすると型が合わなくなる**: `.map(u => u.nickname?.trim()).filter(name => name)` は、結果の型が `(string | undefined)[]` のままで、`string[]` を返す関数では型エラーになる（真偽値だけを返す `filter` は型を絞り込まない）。修正案は、型述語（`(s): s is string => ...`）を付ける、`flatMap` で 1 回にまとめる、のいずれか。先に `filter` してから `map` する形は、`map` の側に `!` が要るなら勧めない。型が通ることを確かめずに出さない。確かめられなければ `unverified` を付ける。
- **配列を何度も走査する形にしない場合**: 一つのループを連鎖に分けると、段ごとに配列を走査する。通常の画面や API のコードでは気にしない。次のいずれかなら、連鎖にはせず、ループの中を段落に分けるだけにとどめる。
  - 途中で `break` / `return` して、残りを読まないこと自体が目的
  - 大きな配列や、毎フレーム・毎レンダリングで走る処理
  - ストリームや SSE のように、届いた順に 1 件ずつ処理するもの
- **副作用のある段階の順序は変えない**: 保存してから通知する、のような順序は、分けても保つ。

## 指摘しない

- すでに段落に分かれていて、各段落が一つの目的のコード。段落ごとの要約コメントは、[comments.md](comments.md) の「消してよいコメント」の例外として残してよい（番号を振っただけでコードの言い換えにすぎないなら、そちらの判断に従う）
- 一つの目的のために 2、3 行が並んでいるだけのもの（絞り込みと 1 回の変換、など）
- 単純な `filter().map()`
- 意図的に一回の走査で処理しているもの（上の「走査しない場合」）

### 例（作者自身のプロジェクトより）

```ts
// features/assets/hooks/use-portfolio-candlestick-chart.ts（収益率モードの分岐）
const areaData = chartData.map((p) => ({ time: p.time, value: ... })); // ① データの換算
const series = chart.addSeries(AreaSeries, { lineColor: ..., ... });   // ② 系列の作成と見た目
series.setData(areaData);                                              // ③ データの投入
series.priceScale().applyOptions({ autoScale: true, ... });            // ④ 軸の設定
seriesRef.current = series;                                            // ⑤ 参照の保存
```

ここで出すべき指摘（`should`、`unverified`）: 表示モードごとの違い（系列の種類、見た目、データ）と、両モード共通の後処理（④⑤。もう一方の分岐とまったく同じ）が、分岐の中で一緒に進んでいる。違いだけを先に決め、共通の部分を 1 回だけ書く形にする。ただし、`ISeriesApi` の型が系列の種類ごとに違うので、共通化すると型が通らないことがある。修正案は型が通るか確かめてから出し、確かめられなければ `unverified` を付ける。①の換算の式そのものの読みにくさは [compression.md](compression.md)、換算を関数に出すことは [extraction.md](extraction.md) の担当で、同じ行範囲なので 1 件にまとめる。

## 修正案の出し方

- 分けたあとのコードを示し、各段落が一つのタスクだけを扱っているかを自分で確かめる。
- 段落の見出しコメントは、段落の目的を 1 行で言えるときだけ付ける。コードの言い換えになるなら付けず、変数名に語らせる。
- 関数に切り出す場合は、[extraction.md](extraction.md) の「修正案の出し方」に従う（コンポーネントの外に置く、など）。
