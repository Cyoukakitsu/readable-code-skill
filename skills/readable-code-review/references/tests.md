# テストの読みやすさ

原則: テストも、初めて読む人が最短で理解できるように書く。テストが読みにくいと、他の人が本体を直すのも、テストを足すのも怖くなる。テストは本体の使い方を示す文書でもあるので、「何を入れると何が返るか」が一目で分かり、失敗したときに原因が分かる形にする。（第 14 章。時刻や乱数を外から渡す話は第 15 章）

読むのは、レビュー対象にテストファイル（`*.test.ts(x)`、`*.spec.ts(x)`、`__tests__/` 配下）が含まれるとき。

分担:
- テスト名と中身の食い違いは [comments.md](comments.md) の「テストの名前と中身の食い違い」の担当（`must`）。このファイルが扱うのは、食い違ってはいないが、名前や構造のせいで読みにくいもの
- 同じ計算の繰り返しは [compression.md](compression.md)、1 つのループや式に複数のタスクが絡む話は [single-task.md](single-task.md)、モジュールスコープの状態は [variables.md](variables.md) の担当
- 同じ行範囲で重なったら 1 件にまとめる

## 先に確かめること

- テストが足りない、カバレッジが低い、本体を変えたのにテストがない、という指摘は出さない。可読性ではないので、このスキルの対象外。「テストを書くべき」とも書かない。
- ESLint のテスト用プラグイン（`vitest/*`、`jest/*`）で有効な規則（`expect-expect`、`no-identical-title`、`valid-title`、`no-focused-tests`、`no-disabled-tests` など）は、SKILL.md の「指摘する前に」と同じく lint に任せる。
- 境界値や入力値の指摘は、本体の関数を読んでから出す。本体が見えなければ `unverified` を付け、重要度を一段下げる。

## 本体向けの規則をテストに当てるとき

テストは、本体と読み方が違う。上から順に 1 つずつ読み、ケースどうしが独立しているほうが読みやすい。次は、他の reference の規則に当てはまって見えても、テストファイルでは指摘しない。

- `describe` / `it` のコールバックが長い（[explain-first.md](explain-first.md)、[extraction.md](extraction.md) の長さの目安）。長さではなく、下の「見つけ方」の観点で見る
- `describe` の直下で `let` を宣言し、`beforeEach` で代入している（[variables.md](variables.md)）。テストフレームワークの標準的な書き方。ただし、テスト間で状態が残って干渉しているなら、下の「本体の側の、テストしにくさのサイン」として扱う
- ケースごとに、同じ形の呼び出しと断言が並んでいる（[compression.md](compression.md) の繰り返しの指摘）。各ケースが 1 つずつ読み切れるなら、畳まない。畳むのは、下の「準備の中に、検証したいことが埋もれている」に当たるときだけ

## 見つけ方

### 準備の中に、検証したいことが埋もれている

`should`。次のどれかに当てはまるとき。

- 同じ形のデータの組み立てが 3 回以上ある、または 1 つのテストで準備のほうが検証より長く、検証に関係のない項目（id、URL、日付、名前）が毎回並んでいる。関係のない項目を隠すファクトリ関数にするか、ケースを `it.each` の表にする。
- 本番のデータを貼り付けた大きな固定データで、結果に関わる項目が数個しかない。必要な項目だけに削る。
- 大きなスナップショット（`toMatchSnapshot()`、`toMatchInlineSnapshot()`）で、何を守っているのか読み取れない。`optional`。守りたい値を `toEqual` / `toMatchObject` で書く。小さなスナップショットや、出力の形そのものが仕様のもの（シリアライザ、コード生成）は指摘しない。

逆向きの落とし穴にも注意する。ファクトリが、そのテストが検証したい値まで既定値で隠していると、テストを読んでも結果を決める値が分からない。そのテストが検証する値は、テストの中に書く。ファクトリが隠してよいのは関係のない項目だけ。重複を減らすことより、1 つのテストをそこだけで読み切れることを優先する。

### 失敗したときに、原因が分からない

`should`。

- 真偽値にしてから検証している: `expect(a === b).toBe(true)`、`expect(list.includes(x)).toBeTruthy()`、`expect(items.length > 0).toBe(true)`、素の `assert(...)`。失敗しても「true のはずが false」としか出ない。`toBe` / `toEqual` / `toContain` / `toHaveLength` / `toMatchObject` に替えると、両辺の値と差分が出る。
- ループの中で `expect` している: `for (const c of cases) expect(f(c.input)).toBe(c.expected)`。失敗しても、どのケースか分からない。`it.each` / `test.each` にすると、ケースの値がテスト名に出る。
- 例外を期待するテストで、`try { await f(); } catch (e) { expect(e.message).toBe("...") }` と書いている。`f()` が例外を出さなかったとき、`expect` が一度も実行されずにテストが通る。`expect(() => f()).toThrow("...")`（非同期なら `await expect(f()).rejects.toThrow("...")`）に直す。何も検証せずに通るテストは、バグを隠しているので `should`。

自作の断言ヘルパーは勧めない。テストフレームワークのマッチャーがすでに差分を出す。同じ検証の繰り返しをまとめるためにヘルパーを作るのは構わないが、その場合は失敗時に入力・期待値・実際の値が出るようにする。

### 入力値が、検証したいことを語っていない

`optional`。ただし、再現できない失敗を生む入力は `should`。

- 結果に影響しない値が目立っている（桁数の多い小数、本番のデータから写した長い id やタイムスタンプ）。結果に関係ない値は、一番単純な値にする。「極端な値」を表したいなら、`1e100` のように、そう読める書き方か、名前を付ける。
- 乱数や現在時刻を入力に使っていて、失敗したときに同じ入力を再現できない（`should`）。固定する。
- 本体の条件（`> 0`、`>= limit`、`length === 0`、`null` / `undefined`）に対して、境界の値、または境界の両側の用例がテストに見当たらない。カバレッジを上げる指摘ではなく、読み手が「境界ではどう動くのか」をテストから読み取れるかどうかの指摘。境界ごとに小さなテストに分ける。
- 入力が、テスト名の条件を本当に満たしているかは [comments.md](comments.md) の担当。

### 1 つのテストで、別々の振る舞いを検証している

`should`。1 つの `it` の中に、準備、実行、検証のまとまりが 2 組以上あり、別の条件を扱っているもの。条件ごとに分けると、失敗したときにどの条件が壊れたかがテスト名で分かる。

次は指摘しない。

- 1 回の実行結果に対する複数の `expect`（返り値の各フィールドを続けて検証するなど）
- 2 つの結果を比べるために 2 回実行するテスト。その比較が 1 つの振る舞いなら 1 つのテストでよい

### テスト名が、状況も期待も語っていない

`test1`、`works`、`ok`、`should work correctly`、`正しく動く` のように、どんな状況で何が起きるべきかが読み取れない名前は `should`。名前の一部が曖昧な程度なら `optional`。

目安は、`describe` に対象の関数やコンポーネントの名前、`it` に「どんな状況で、どうなるか」を置く形。`Test_<関数名>_<状況>` という書き方を強いない。名前が長くなることも指摘しない（他のコードから呼ばれず、失敗時に表示されるのでコメントの役目をする）。日本語・中国語・英語のどれか、`it("should ...")` か `it("returns ... when ...")` かは、プロジェクトの慣習に従う。

### 本体の側の、テストしにくさのサイン

`optional`。テストが苦労している跡から、本体の設計を指摘する。指摘は本体の該当箇所に付け、テストは根拠として挙げる。

- `beforeEach` / `afterEach` で、モジュールスコープの状態を毎回リセットしている（`vi.resetModules()`、キャッシュや配列の手動クリア）。リセットしないとテスト同士が干渉する。[variables.md](variables.md) の指摘と 1 件にまとめる。
- 1 つの関数のテストのために 5 つ以上のモックやスパイを立てている。その関数が依存しすぎている。
- テストのためだけに内部状態を公開している（`_forTest`、テスト専用の getter、`__testOnly` という名前の `export`）。公開されているインターフェースだけでテストするか、中の計算を純粋関数に出して、それをテストする。
- 現在時刻や乱数を関数の奥で直接読んでいて、テストがそのためにグローバルを書き換えている（`vi.spyOn(Date, "now")` が何か所にも散らばっている、など）。現在時刻を引数（既定値は現在時刻）で受け取る形にし、読む場所を一番外側の 1 か所に集める案を出す。テストでは固定した値を渡せる。`vi.useFakeTimers()` と `vi.setSystemTime()` の 1 行で済んでいるなら指摘しない。時刻を読む場所が 1 か所で、そこが処理の入口なら、それも指摘しない。

## 指摘しない

- テストがない、カバレッジが低い、という指摘（上の「先に確かめること」）
- 1 回の実行結果に対する複数の `expect`
- 期待値の根拠を書いたコメント。次のように、値がどう決まるかを書いたものは残す。[comments.md](comments.md) の「消してよいコメント」には当たらない

  ```ts
  // features/assets/lib/__tests__/calculations.test.ts
  // 总成本 = 100×10 + 200×5 = 2000
  // 总数量 = 15
  // 均价 = 2000 / 15
  expect(result.total_quantity).toBe(15);
  expect(result.total_cost).toBe(2000);
  expect(result.avg_price).toBeCloseTo(133.33, 2);
  ```

- ケースを並べた表（`it.each` の表、同じ形の呼び出しが並ぶテスト）。繰り返しが多く見えても、各ケースが 1 行で読めるなら、関数にまとめて畳まない。テストでは、重複の少なさより、1 つずつ読み切れることを取る
- 文字列で独自の記法を作ってテストを短くする書き方（`check("1, 2, -1", "3, 2, 1")` のように、文字列を解析するヘルパーを経由するもの）を勧めない。TS/JS では、配列やオブジェクトのリテラルをそのまま渡せば足りる。解析するコードが増え、その解析にもバグが入りうる
- テスト専用の `export` を「未使用」とみなして削除を勧めない（[less-code.md](less-code.md) の「先に確かめること」と同じ）
- テスト駆動開発（TDD）をしているかどうか

## 修正案の出し方

- 直したテストを示し、元と同じ振る舞いを検証していることを自分で確かめる。準備を減らして検証が弱くなっていないか、`it.each` に直しても全ケースが残っているかを見る。
- テスト名の改善案は、名前だけ読んで、状況と期待が分かる形で出す。
- 本体の変更が必要な提案（時刻を引数にするなど）は、テストを直す案とは別に書き、影響範囲（呼び出し元の件数）を添える。
