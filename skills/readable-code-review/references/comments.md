# コメント

原則: コメントは、コードからは読み取れないことを書く場所。「何をしているか」はコードを読めば分かり、読む力が上がるほど（人間でも AI でも）そのコメントの価値は下がる。残す価値があるのは「なぜそうしたか」「何にハマったか」「実測値はどうだったか」「既知の欠陥」、そしてコードと照らし合わせられる意図。（第 5・6 章）

## 最優先: コメントとコードの食い違い

コメントに意図、コードに実装が書いてあれば、両者のずれはバグか、古くなったコメントのどちらかを示す。どちらでも読み手を誤解させるので `must`。

- コメントが述べる動作・値・条件を、実際のコードと一つずつ突き合わせる。ライブラリのオプションに付いたコメントは、そのオプションの実際の意味と照らす。
- diff をレビューするときは、コードが変わったのにすぐ上のコメントが変わっていない箇所を探す。
- JSX の `{/* */}` コメントも対象に含める。複数の区画をまとめて紹介する見出しコメント（「A + B + C」のように並べたもの）は、並び順や含まれる要素が実際の JSX の構造と合っているかを確認する。レイアウトを組み替えたあとに古いまま残りやすい。
- どちらが正しいか判断できなければ、両方の可能性を書き、作者に確認するよう促す。

### 例（作者自身のプロジェクトより）

```ts
// features/assets/hooks/use-total-asset-card.ts
staleTime: 60 * 1000, // 数据在内存中保留 1 分钟，避免数据过期
gcTime: 5 * 60 * 1000, // 数据在内存中保留 5 分钟，导航回来时直接用
```

ここで出すべき指摘: 2 つの別の設定に「メモリに保持する」という同じ説明が付いている。TanStack Query では、`staleTime` はデータを新しいとみなして再取得しない時間、`gcTime` は使われなくなったキャッシュをメモリに残す時間で、`staleTime` 側のコメントは実際の意味と違う。同じプロジェクトの `use-asset-table.ts` の `// 缓存 1 分钟，不会重新发起请求` のほうが正確なので、表現をそろえる。

## 書くべき「なぜ」が欠けている

コードだけ見ると不自然、またはほかの書き方のほうが良さそうに見える箇所で、理由が書かれていなければ指摘する（`should`）。

- 一見遠回りな実装、あえて遅いアルゴリズム、ライブラリのバグ回避
- 根拠の見えない数値（上限、タイムアウト、キャッシュ時間、リトライ回数）。`MS_PER_SECOND = 1000` のような自明な定数は対象外
- 同じ種類の設定値がファイルごとに違う（あるフックは 30 秒、別のフックは 5 分）のに、なぜ違うのか書かれていない
- 呼び出し側が知らないと事故になる性質: 長時間ブロックする、外部サービスを呼ぶ、呼ぶたびに課金される、冪等でない。まず名前で表せないか検討し（[naming.md](naming.md)）、名前に入りきらない分をコメントにする

同じ種類の数値が何か所もあるときは、1 件ずつ挙げずに 1 件の指摘にまとめ、該当箇所を列挙する。

注意: 理由そのものを推測して書かない。理由を知っているのは作者だけで、レビュー側がもっともらしい理由を作ると、間違っていても正しく見えてしまう。修正案は「ここに〇〇の理由を書く」という形の空欄にする。

```ts
// app/api/assets/news/route.ts
.slice(0, 10); // 最多10个
```

ここで出すべき指摘: コメントはコードの言い換えで、なぜ 10 なのか（API の料金か、レート制限か、表示の都合か）が分からない。修正案は `const MAX_NEWS_SYMBOLS = 10; // TODO: 10 にした理由を書く` のような形にし、理由は作者に委ねる。

## 消してよいコメント

コードをそのまま日本語・中国語・英語に訳しただけのコメントは `optional` で削除を提案する。JSDoc で `@param id - ID` のように型と名前を繰り返しているだけのものも同じ。

例外として、次は残す。

- 密度の高いコード（正規表現、ビット演算、凝った分割・結合）の上に付いた、高レベルの意図の要約。コードから読み取れる内容でも、読み手が自分で解読せずに済む
- ループや処理のかたまりの目的を 1 行でまとめた要約コメント
- 公開 API の JSDoc で、ドキュメント生成や IDE の補完に使われているもの

一部だけが言い換えのコメントは、言い換え部分だけを削るよう提案する。

```ts
// features/ai/components/agent-selector.tsx
e.stopPropagation(); //  阻止事件冒泡（事件往上传播），为了防止触发卡片的点击事件
```

前半の「イベントのバブリングを止める」は `stopPropagation` の説明にすぎない。後半の「カードのクリックイベントを発火させないため」が理由で、ここだけ残せばよい。

## 正確さ（第 6 章）

コメントがあっても、読み手が別の意味に取れるなら役に立たない。次は `optional`。ただし公開 API や他チームが使う関数の契約が曖昧な場合は `should` に上げる。

- 指す対象が曖昧な代名詞（「それ」「これ」「it」）
- 中身のない動詞（「調整する」「処理する」「整える」「handle」）。どう変えるのかというルールを直接書くよう提案する
- 境界の動作が決まらない説明（「行数を返す」で空ファイルや末尾改行がどうなるか分からない）。数える対象を具体的に書くか、境界を含む入出力例を 1 つ付けるよう提案する
- 入出力例を付けるなら、重複、空、境界値を含み、ほかの解釈と区別できる例を選ぶ

## 呼び出し側の真偽値・数値リテラル

`connect(10, false)` のように、意味の分からないリテラル引数が並ぶ呼び出しは指摘する。修正案の優先順位は次のとおり。

1. 関数の定義を変えられるなら、オプションオブジェクトにする（`connect({ timeoutMs: 10, useEncryption: false })`）。TS ではこれが標準的な書き方で、引数名が呼び出し側に残る
2. 外部ライブラリなど定義を変えられないなら、`/* timeoutMs = */ 10` の形で値の前にコメントを置く。値の後ろに置く `false /* useEncryption */` は、`false` がどちらの意味か曖昧になるので勧めない

`setOpen(false)` や `setIsLoading(true)` のように、関数名で引数の意味が決まるものは対象外。

## 欠陥マーカー

`TODO:` / `FIXME:` / `HACK:` / `XXX:` があること自体は指摘しない。既知の欠陥を正直に書くのは良いこと。

指摘するのは次の場合だけ（`optional`）。

- 中身のない `// TODO` だけで、何をすべきか、なぜ今やらないのかが書かれていない
- コードを見ると明らかに一時しのぎなのに、マーカーも説明もない

## AI が書いたコメントについて

コメントとコードを同じ AI に書かせると、AI はコードから意図を逆算するしかない。バグのあるコードにも、それをもっともらしく説明するコメントが付き、「コメントとコードのずれでバグに気づく」という仕組みが働かなくなる。

- コメントが、コードの動作を正確に説明しているが、要件として正しいかは分からない場合、それを「良いコメント」と判断しない。
- 要件や設計資料（Issue、PR の説明、仕様書）がレビュー対象に含まれていれば、コメントをコードではなく要件と照らし合わせる。

## 指摘しないもの

- コメントの言語（日本語・英語・中国語）。ただし 1 ファイル内で混在していて読みにくい場合は、プロジェクトの慣習に合わせるよう `optional` で提案してよい
- コメントの書式（`//` か `/* */` か、句点の有無、行末か行頭か）
- 小さなファイルや自明なモジュールにファイル先頭の概要コメントがないこと
- 悪い名前を補っているコメント。コメントを直すのではなく改名を提案する（[naming.md](naming.md)）
