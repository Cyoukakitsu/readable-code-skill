# 下位問題の抽出

原則: 関数の名前が約束している目的と、直接は関係のない処理（下位問題）を、その関数の中に置かない。上位のコードは「何をするか」だけを語り、「どうやるか」は名前の付いた別の関数に任せる。逆に、分けすぎて読み手が関数の間を行き来することになるなら、それも読みにくさとして指摘する。（第 10 章）

ネストを浅くするための切り出しは [control-flow.md](control-flow.md)、同じ計算の繰り返しをまとめるのは [compression.md](compression.md) の担当。このファイルが扱うのは、ネストも重複もないのに、関数の中で目的と関係のない処理が場所を取っているもの、そして切り出しすぎたもの。同じ行範囲で重なったら 1 件にまとめる。

## 判断の基準

切り出すかどうかは、再利用するかどうかでは決めない。基準は「呼び出し側を読むとき、切り出した関数の中に入らずに済むか」。

- 名前が中身の代わりに語れるなら、一度しか使わない処理でも切り出す価値がある。「再利用されないから切り出さなくてよい」という理由で指摘を見送らない。
- 名前が中身とほとんど同じことしか言えない（中身が 1、2 行で、名前がその言い換え）なら、切り出しても読み手の手間は減らない。切り出しを提案しない。
- 切り出しを提案するときは、切り出したあとの呼び出し側を示し、それが関数名だけで読めるかを自分で確かめる。読めないなら、名前が悪いか、分け方が悪い。

## 目的と関係のない処理が混ざっている

関数（React のコンポーネントやフック、`useEffect` の本体、Route Handler を含む）の中で、次のような処理が業務の流れの間に挟まっていて、読み手がそれを解読しないと先に進めないものを指摘する（`should`）。

- 数式（単位の変換、割合、距離、丸め）
- 正規表現の連続、文字列の組み立てや分解
- 日付の計算や書式の変換
- ブラウザや標準 API の生の操作（`document.cookie` の分解、`localStorage` と `JSON.parse` の組み合わせ、`fetch` → `res.ok` の確認 → `res.json()` の手順を毎回書いているもの）
- 大きな設定オブジェクトのリテラル（チャートやライブラリの見た目の設定が数十行続くもの）

次の場合は指摘しない。

- 挟まっている処理が 2、3 行で、読めばすぐ分かるもの
- 関数の目的そのものである処理。`formatPrice()` の中の書式変換は下位問題ではない。何が下位問題かは、関数名が約束している目的から判断する

### 例（作者自身のプロジェクトより）

```ts
// features/assets/hooks/use-portfolio-candlestick-chart.ts（useEffect の本体、約 85 行）
const chart = createChart(chartContainerRef.current, {
  width: ..., height: 350,
  layout: { ... }, grid: { ... }, timeScale: { ... }, rightPriceScale: { ... },
}); // 見た目の設定が約 20 行
...
} else {
  const areaData = chartData.map((p) => ({
    time: p.time,
    value: totalCost > 0
      ? parseFloat((((p.close - totalCost) / totalCost) * 100).toFixed(2))
      : 0,
  }));
```

ここで出すべき指摘（`should`）: この `useEffect` の目的は「チャートを作り、表示モードに応じた系列を載せ、サイズの変化に追従させる」こと。見た目の設定の約 20 行と、終値を収益率に換算する計算は、その目的と関係のない下位問題で、読み手は流れを追う前にそれを読まされる。設定はモジュールのトップレベルの定数 `CHART_OPTIONS` に、換算は `lib/` の `toReturnPctSeries(chartData, totalCost)` に移す。収益率の式そのものの読みにくさ（[compression.md](compression.md)）や、2 つの分岐で重複している `priceScale().applyOptions`（同）と同じ行範囲なので、1 件にまとめる。

### 修正案の出し方

- 切り出した関数は、コンポーネントやフックの外（モジュールのトップレベル、またはプロジェクトの既存の `lib/` や `utils/`）に置く。コンポーネントの中で定義すると、レンダリングのたびに作り直され、依存配列にも入れなければならなくなる。
- 修正案には、切り出した関数のシグネチャと、何を返すかを 1 行で書く。名前は [naming.md](naming.md) の動詞の目安に従う。
- 設定オブジェクトのリテラルは、関数ではなくモジュールのトップレベルの定数にする。

## 自作する前に、すでにあるものを探す

汎用の処理を切り出すよう提案する前に、次を確認する。確認せずに「`utils/` に関数を作る」と提案しない。

1. プロジェクトの `lib/` や `utils/` に、同じことをする関数がすでにないか。あるのに使わず手書きしているなら、それを使うよう指摘する（`should`）。
2. 標準 API で済まないか。`URLSearchParams`（クエリ文字列の組み立て）、`Intl.NumberFormat` / `Intl.DateTimeFormat`（数値・日付の書式）、`structuredClone`（深いコピー）、`Array.prototype.at` / `findLast`、`crypto.randomUUID`、`AbortSignal.timeout` など。手書きの実装が標準 API と同じことをしているなら、置き換えを提案する（`optional`。手書きの実装にバグがあるなら `should` 以上）。`Object.groupBy` のように比較的新しい API は、プロジェクトの実行環境や `tsconfig` の `lib` で使えるかを確かめてから提案する。確かめられなければ `unverified` を付ける。
3. `package.json` の依存関係（`date-fns`、`lodash` など）に、すでにあるものがないか。

同じ汎用処理が 2 か所以上で手書きされているなら、1 か所にまとめるよう提案する（`should`）。まとめておけば、その処理にバグがあっても 1 か所で直せる。

### 例（作者自身のプロジェクトより）

```ts
// features/assets/hooks/use-portfolio-candlestick-chart.ts
const to = new Date().toISOString().split("T")[0];

// features/assets/lib/date-utils.ts（getFromDate の中）
const from = new Date(now.getTime() - daysMap[range] * 24 * 60 * 60 * 1000);
return from.toISOString().split("T")[0];
```

ここで出すべき指摘（`should`、`unverified`）: 「日付を `YYYY-MM-DD` にする」処理が 2 つのファイルで手書きされている。`date-utils.ts` に `toDateString(date: Date): string` のような関数を 1 つ作り、両方から呼ぶ。あわせて、`toISOString()` は UTC の日付を返すので、日本時間の 0 時から 9 時の間は前日の日付になる。意図した動作かどうかはコードから決められないので、作者に確認する。1 か所にまとめておけば、ローカル時刻に直すときも 1 か所の修正で済む。

## 使いにくい API は包む

標準や外部ライブラリの API が直感に反する（読むたびに仕様を思い出す必要がある）なら、業務コードで直接使わず、薄いラッパーで包むよう提案する（`should`）。典型は `document.cookie`（読むときは文字列を自分で分解し、代入は上書きではなく追加になり、削除は有効期限を過去にする）。

- ラッパーを提案するのは、同じ API の生の操作が 2 か所以上にあるか、1 か所でも読み手が仕様を知らないと読めない場合。
- 型がしっかりしたライブラリの API（TanStack Query、Supabase のクライアントなど）を、ただ名前を変えるためだけに包むことは提案しない。下の「切り出しすぎ」に当たる。

## 切り出しすぎ

次のような関数は、呼び出しをたどる手間を増やすだけなので、呼び出し元に戻すよう提案する（`optional`。3 段以上たらい回しになっていて、読み手が処理の中身にたどり着くまでに何度も移動しなければならないなら `should`）。

- 1 か所からしか呼ばれず、中身が 1、2 行で、名前が中身の言い換えにすぎない関数
- 受け取った引数をそのまま別の関数に渡すだけの関数（`function getUser(id) { return fetchUser(id); }`）
- `A` が `B` を呼び、`B` が `C` を呼ぶだけで、各段が何も足していない連鎖

次の場合は、薄く見えても指摘しない。

- 型ガード（`function isAsset(x): x is Asset`）。型の絞り込みは関数でしか書けない
- テストでモックを差し込むための境界になっているもの（外部 API の呼び出しを 1 つの関数に閉じ込めているなど）。呼び出し元のテストを見て確かめる。確かめられなければ `unverified` を付けて指摘を見送る
- フレームワークの都合で必要なもの。Server Action、Route Handler、カスタムフック（`useQuery` を包んで `queryKey` を 1 か所に集めるフックは、薄くても意味がある）
- パッケージやモジュールの公開 API として、外から呼ばれているもの

### 修正案の出し方

- 呼び出し元に戻したあとのコードを示し、移動しなくても読めるようになることを 1 行で書く。
- 戻すと呼び出し元の関数が長くなりすぎる場合は、薄い関数を全部消すのではなく、意味のある単位で 1 つにまとめ直す案を出す。
