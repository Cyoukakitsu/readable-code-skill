# 書かなくていいコード

原則: いちばん読みやすいコードは、書かれていないコード。今の要件にない機能のための引数や抽象化、使われなくなった残骸は、読み手に「これはどこで使われるのか」を考えさせるだけで、何も返さない。（第 13 章）

AI にコードを書かせると、頼んでいないオプション引数や「将来の拡張用」の口が簡単に増える。書くコストが下がっても、読むコストは下がらない。このファイルは、そうした「今は誰も使っていないもの」を見つけるためのもの。

分担:
- 同じ計算の繰り返しは [compression.md](compression.md)、同じ汎用処理の手書きの重複と、標準 API・既存ライブラリへの置き換えは [extraction.md](extraction.md) の担当
- 型や取り決めのせいで起こりえない分岐は [defensive-code.md](defensive-code.md)、処理の流れの中で役目を終えた分岐は [explain-first.md](explain-first.md) の担当
- 同じ行範囲で重なったら 1 件にまとめる

## 先に確かめること

「使われていない」と言うには、呼び出し元をすべて見る必要がある。レビュー対象のファイルだけでは、ほとんどの `export` が使われていないように見える。

- プロジェクト全体を検索できるなら、呼び出し元を検索してから指摘する。指摘には、検索した範囲と見つかった呼び出し元の数を書く。
- 検索できないなら、`export` された関数・定数・型が使われていないという指摘は出さない。引数やオプションについては、見えている呼び出し元だけを根拠に `unverified` を付け、重要度を一段下げて指摘してよい。
- 未使用のローカル変数・import と、関数の中で一度も参照されていない引数は `tsc`（`noUnusedLocals` / `noUnusedParameters`）や ESLint（`no-unused-vars`）の仕事なので扱わない（SKILL.md のとおり）。
- 未使用の `export` を検出するツール（`knip`、`ts-prune` など）がプロジェクトに入っていれば、未使用の `export` はそちらに任せる。入っておらず、未使用の `export` が複数見つかったなら、レポートの末尾で導入を 1 行だけ提案する（設定ファイルは編集しない）。

## 先回りの実装

今の要件にない機能のための口が開いているもの。

### 誰も渡していない引数・オプション

省略可能な引数や `options` オブジェクトのフィールドで、どの呼び出し元も渡していないもの、または全員が同じ値を渡しているものは、削除して固定するよう提案する（`optional`）。

ただし、その引数があるせいで、読み手が実際には起きない動作を信じてしまう場合は `should`。引数名やコメントが「〜のときは〜を使う」と約束しているのに、誰も渡していないので、その動作が一度も起きていないものが典型。これは「消すべき先回り」なのか「渡し忘れたバグ」なのかをコードからは決められない。片方に決めつけず、両方の可能性を書いて作者に確認する（SKILL.md の「業務上の意図にかかわる食い違い」と同じ扱い）。

#### 例（作者自身のプロジェクトより）

```ts
// features/assets/lib/date-utils.ts
export function getFromDate(range: Range, firstTransactionDate?: string): string {
  ...
  if (range === "MAX") {
    // 使用最早交易日，若无则默认 2020-01-01
    return firstTransactionDate ?? "2020-01-01";
  }
  ...
}

// features/assets/hooks/use-portfolio-candlestick-chart.ts
const from = getFromDate(range);
```

ここで出すべき指摘（`should`、`unverified`: 他の呼び出し元）: コメントは「MAX のときは最初の取引日を使う」と約束しているが、見えている唯一の呼び出し元は `firstTransactionDate` を渡していない。そのため MAX の開始日は、最初の取引日とは関係なく常に `2020-01-01` になる。渡し忘れなら、この hook が受け取っている `allTransactions` から最初の取引日を求めて渡す（`Transaction` に日付のフィールドがあることは未確認）。不要な先回りなら、引数を消し、コメントも「MAX は 2020-01-01 から」に直す。どちらが意図かは作者に確認する。

### 実装が 1 つしかない抽象化

次のようなものは、抽象化を外して直接書くよう提案する（`optional`）。読み手は、存在しない別の実装を探しに行くことになる。

- 実装クラスが 1 つしかない `interface` や抽象クラス
- 1 種類のものしか作らないファクトリ、エントリが 1 つしかない戦略マップ
- 呼び出し元がすべて同じ型を渡しているジェネリクスの型引数
- 常に同じ値になっている設定フラグや環境変数による分岐

次の場合は指摘しない。

- テストでモックを差し込むための境界になっているもの（[extraction.md](extraction.md) の「切り出しすぎ」の例外と同じ）
- フレームワークの都合で必要なもの（NestJS のプロバイダの注入トークン、Next.js の規約ファイル）
- パッケージの公開 API として、外から使われるもの
- 2 つ目の実装が Issue や PR の説明などで具体的に予定されているもの（レビュー対象に含まれていれば確認する）

### 計測していない性能対策

自前のキャッシュ（モジュールスコープの `Map` など）、バッチ処理、仮想化などが入っているのに、対象のデータが小さい、または遅いという根拠がコードやコメントにないものは、`optional` で「計測の根拠があるか」を作者に尋ねる。根拠がなければ外すことを提案する。サーバー側のモジュールスコープのキャッシュは、リクエストをまたいで値が残る問題を [variables.md](variables.md) で先に確かめる。

`useMemo` / `useCallback` は、それだけでは指摘しない。付けるかどうかはチームの方針や React Compiler の有無で変わり、外しても読みやすさはほとんど変わらない。TanStack Query の `staleTime` などライブラリの設定も、性能対策の先回りとしては扱わない。

## 残骸

使われなくなったのに残っているもの。

- **コメントアウトされたコード**: 履歴は git に残っているので削除を提案する（`should`）。読み手は「戻す予定があるのか」「なぜ止めたのか」を考えさせられる。止めた理由に価値があるなら、コードではなく一文のコメントにする。
- **呼び出し元がない関数・分岐**: 検索して呼び出し元が 0 件だと確かめられたものは削除を提案する（`should`）。「旧バージョン用」「念のため残す」と書かれた関数も同じ。
- **常に同じ側に入る分岐**: 原因が型なら [defensive-code.md](defensive-code.md)、処理の流れなら [explain-first.md](explain-first.md) の指摘として出す。

## 重複をまとめる修正案の出し方

重複の検出は [compression.md](compression.md) と [extraction.md](extraction.md) に任せる。ここでは、まとめる修正案を出すときの注意だけを書く。

- 既存の呼び出し元を壊さない形を優先する。引数名や意味を変えるより、既存の関数にデフォルト値付きの引数を足すほうが、変更が少ない。まとめると呼び出し元の変更が必要になるなら、件数を「影響範囲」に書く。
- 今たまたま同じ形をしているだけで、変わる理由が別々のもの（画面表示用の書式と CSV 出力用の書式など）は、まとめるよう勧めない。片方の仕様が変わったとき、もう片方を巻き込む。迷ったら、まとめずに `optional` で「同じ理由で変わるならまとめる」と書くにとどめる。

## 指摘しない

- 今の要件のために使われている引数・オプション（呼び出し元が 1 か所でも実際に値を渡しているもの）
- ライブラリやフレームワークのインターフェースを満たすために必要な引数（使わなくても、シグネチャが決まっているもの）
- 既存のコマンドや CLI ツールで済む作業を自前のスクリプトで書いている、という指摘。コードレビューの対象外とする（`scripts/` のスクリプト自体がレビュー対象で、既存の CLI や npm scripts と同じことをしているなら、`optional` で 1 行触れる程度）

## 修正案の出し方

- 削除を提案するときは、確かめた呼び出し元（検索した範囲と件数）を書く。確かめられないなら `unverified`。
- 「コメントアウトして残す」形の修正案は出さない。消すか残すかのどちらかにする。
- 削除する引数・オプションのせいで、コメントや型も変わるなら、それも修正案に含める（上の `getFromDate` の例ではコメントも直す）。
