# 変数

原則: 読み手が頭の中で追いかける変数を減らす。変数が多いほど、見える範囲が広いほど、書き換えられる回数が多いほど、読み手は「いまこの変数に何が入っているか」を覚え続けなければならない。（第 9 章）

この章の規則の一部は ESLint で検出できる（`no-var`、`prefer-const`、`no-unused-vars`、`block-scoped-var`）。lint との分担は SKILL.md の「指摘する前に」に従う。このファイルが扱うのは、lint では判断できない「消してよいか」「縮めてよいか」「書き換えが読み手を迷わせているか」のほう。

## 不要な変数を消す

### 意味のない一時変数

1 回代入され、1 回だけ使われ、名前が式以上の情報を足していない変数は、式を直接書くよう提案する（`optional`）。

次の場合は消さない。指摘もしない。

- 名前が式の意味を説明している（説明変数・要約変数）。こちらは [compression.md](compression.md) の担当で、消すとむしろ読みにくくなる。判定基準は「名前を読まずに式だけを見て、同じことがすぐ分かるか」。
- ある時点の値を固定している。`const now = new Date()` を 2 か所以上で使っていれば、式に戻すと別々の時刻になり動作が変わる。`await` の結果、乱数、`Date.now()`、ミュータブルなオブジェクトから読んだ値も同じ。1 回しか使っていないかを必ず数えてから指摘する。
- `await` の結果を受ける変数で、式に埋め込むと `await` が式の途中に入るもの（`foo(await bar())`）。どちらが読みやすいかは好みの差が大きいので触れない。

### 中間結果と制御フラグ

`found`、`done`、`indexToRemove` のように、ループの外へ情報を運ぶためだけの変数は、見つけた時点で `return` / `break` するよう提案する（`should`）。TS/JS では、組み込みメソッドで変数ごと消せることが多いので、修正案はそちらを優先する。

- 存在するか → `some` / `includes`
- 最初の 1 件 → `find` / `findIndex`
- 条件に合うものを除いた配列 → `filter`（元の配列を書き換えてよいかは呼び出し元を確認する）

次のフラグは指摘しない。

- 非同期の処理をまたいで状態を伝えるもの。`useEffect` の `let cancelled = false` と cleanup での `cancelled = true`、`AbortController`、二重送信防止の `isSubmitting` など。ループの制御ではなく、別のタイミングで動くコードとの連絡に使っている。
- ループのあとに後片付けや集計が続いていて、途中で `return` するとそれが飛ばされるもの。`return` に置き換える修正案を出す前に、ループの後ろに何があるかを確認する。

## スコープを縮める

### モジュールスコープのミュータブルな変数

本書の「グローバル変数を避け、クロージャで閉じ込める」は、ES Modules では形が変わる。モジュールのトップレベルはもともとファイルの外から見えないので、即時実行関数で包む修正案は出さない。問題になるのは、トップレベルの `let`（や書き換えられるオブジェクト）が、想定より広い範囲で共有されている場合だ。

- サーバー側のコード（Next.js の Route Handler・Server Action・Server Component、NestJS のサービス、Edge/Node のハンドラ）で、トップレベルの変数にリクエストやユーザーごとの値を書き込んでいる → `must`。プロセスが生きている間はリクエストをまたいで共有され、別のユーザーの値が混ざる。キャッシュとして意図的に共有しているなら、その意図が名前かコメントで分かるかを見る。分からなければ `should` で、意図の明示を求める。
- クライアントのコンポーネントで、インスタンスごとに持つべき値をトップレベルの `let` に置いている → `must`。同じコンポーネントを 2 つ並べると値を共有してしまう。`useState` / `useRef` に移す。
- 書き換えられないトップレベルの定数（設定値、ルックアップテーブル）は問題ない。指摘しない。

### 使う場所の近くで宣言する

関数の先頭にまとめて宣言され、使われるのがずっと後ろ（おおむね 10 行以上あと）の変数は、最初に使う直前へ移すよう提案する（`optional`）。間に別の処理が挟まっていて、読み手がその間ずっと変数を覚えておく必要がある場合に限る。

- React のフックはコンポーネントの先頭で、条件分岐の外で呼ぶ必要がある（Rules of Hooks）。`useState` などが先頭に集まっていても指摘しない。
- 宣言を移すと評価のタイミングが変わるもの（副作用のある関数呼び出し、`await`、時刻の取得）は、移動の前後で結果が同じかを確認してから提案する。

### ブロックスコープ

`var` は `no-var` の範囲なので lint との分担に従う。lint で検出できないのは、ループや `if` の中でしか使わない変数を外側で宣言しているもの。内側へ移すよう提案する（`optional`）。ただし、反復をまたいで値を持ち越す必要がある変数は外側にあるのが正しい（下の例）。

## 値を一度だけ書き込む

- 再代入のない `let` は `prefer-const` の範囲なので lint との分担に従う。
- 1 つの `let` を何度も書き換え、段階ごとに中身の意味が変わっているもの（小計 → 割引後 → 税込）は、段階ごとに名前を付けた `const` に分けるよう提案する（`should`）。途中のどこかで、変数名と中身が食い違う段階があれば `must`（[naming.md](naming.md) の「名前と中身のずれ」と同じ扱い）。たとえば `price` が税抜きのまま税込みとして使われうる場合。
- `const` でも、オブジェクトや配列の中身は書き換えられる。`const` だからといって追跡しやすいとは見なさない。組み立て途中のオブジェクトを複数の関数に渡し、それぞれがプロパティを足したり書き換えたりしているものは、「どこで何が入ったか」を追う手間が `let` の再代入と同じなので指摘する（`should`）。React の state やフックの戻り値を直接書き換えているものは、読みやすさではなくバグなので `must`。

次の再代入は指摘しない。

- ループの累積（合計、`buffer` への追記、カウンタ）。値が変わること自体が処理の目的。
- シミュレーションや状態遷移のように、反復ごとに前の値から次の値を計算するもの。無理に `const` に分けると、反復回数だけ変数が必要になる。
- `let x; try { x = ...; } catch { ... }` の形。TS/JS には式として使える `try` がないための書き方。関数に切り出して `return` すれば `const` にできるが、提案するなら `optional`。

### 例（作者自身のプロジェクトより、指摘しないケース）

```ts
// features/ai/components/analysis-shell.tsx（SSE の読み取り）
for (const line of lines) {
  if (line.startsWith("event: ")) {
    currentEvent = line.slice(7).trim();
  } else if (line.startsWith("data: ") && currentEvent) {
    const data = JSON.parse(line.slice(6));
    ...
```

`currentEvent` はループの外で宣言され、ループの中で書き換えられているが、指摘しない。SSE では `event:` 行と `data:` 行が別の行で届くので、前の行で読んだイベント名を次の行まで持ち越す必要がある。スコープを 1 回の反復に縮めると動かなくなる。一方 `data` は 1 行の中で完結しているので、ブロックの中で `const` になっていて正しい。（このファイルのネストの深さについては [control-flow.md](control-flow.md) の例を参照）

## 毎回変わる値を依存に入れる（React）

レンダリング中に作った配列・オブジェクト・関数（`filter` / `map` の結果、`{}` や `[]` のリテラル）を `useEffect` / `useMemo` / `useCallback` の依存配列に入れていると、毎回新しい参照になり、依存は実際には毎レンダリング変わる。読み手は「値が変わったときだけ動く」と読むが、実際は毎回動く。

- チャートの作り直し、イベント購読、ネットワーク通信など、再実行が重い処理なら `must`。軽い処理なら `should`
- 修正案: 値を作る式を `useMemo` で包む。または、配列そのものではなく安定した値（長さ、`join` した文字列、id）を依存にする。`filter` で作った中間の配列も同様に安定させないと、`useMemo` の依存になっていて意味がなくなる
- 手がかり: ESLint の `react-hooks/exhaustive-deps` が「依存が毎回変わる」という warning を出していれば、同じ問題
- 親から渡される props の参照が安定しているかは、この場では確認できないことが多い。確認できなければ `unverified` を付ける

## 修正案の出し方

- 変数を消す・移す・分ける修正案を出すときは、読み手が同時に追う変数がいくつ減るかを 1 行で書く（「`found` と `indexToRemove` がなくなり、ループの中だけを読めばよくなる」など）。減らないなら提案しない。
- 3 つの観点（消す・縮める・一度だけ書く）が同じ関数に重なっているときは、1 件にまとめて、変数ごとに何をするかを並べる。修正後のコードは 1 つだけ示す。
