# 命名

原則: 名前は、中身が何か、呼び出しコストがどれくらいかを、コメントなしで読み手に伝えるべき。そのうえで、読み手が別の意味に取れない名前にする。（第 2・3 章）

## データを返す関数の動詞

TS/JS のプロジェクトで最もよくある問題は、何にでも `get` を使うこと。`getXxx` を見ても、遅いのか、失敗しうるのか、エラー処理が必要なのか判断できない。

動詞でコストを伝える:

| 動詞 | 意味 | 失敗しうるか / 非同期か |
| --- | --- | --- |
| `fetch` | 外部へのネットワークリクエスト（HTTP、外部 API） | しうる / たいてい非同期 |
| `load` / `query` | ストレージからの読み込み（DB、ファイル、キャッシュ） | しうる / たいてい非同期 |
| `compute` / `calc` / `build` | 純粋なローカル計算 | しない / 同期 |
| `get` | すでにメモリ上にあるものへの安価なアクセス（アクセサ、Map の参照） | しない / 同期 |

この表はデフォルトの目安にすぎない。プロジェクトにすでに独自の語彙があるならそれに従い、その中での不統一だけを指摘する。

### 例（作者自身のプロジェクトより）

```ts
// lib/news-fetcher.ts — 外部通信するので fetch ✅
export async function fetchNews(query: string) { ... }

// features/ai/lib/getNews.ts — fetchNews を包んでいるのに get ❌
export const getNews = tool({ execute: ... fetchNews(...) })

// features/assets/server/assets.ts — DB を読むのに get
export async function getAssets() { ... supabase.from("assets") ... }

// features/assets/lib/date-utils.ts — ローカル計算だけなのに get ❌
export function getFromDate(range) { ... }
```

ここで出すべき指摘:
- `getFromDate` → `computeFromDate`（純粋な計算）
- `getAssets` → `loadAssets` または `queryAssets`（ストレージの読み込み）
- `getNews` → 中身は `fetchNews` で外部通信なので、動詞は `fetch` にする。このファイルは `tools: { getStockPrice, getFinancials, getNews }` の省略記法で登録されていて、変数名がそのままモデルの見るツール名になる。ツール名は人間向けのラベルであると同時に、モデルがツールを選ぶ手がかりでもあるので、動詞とデータ源が分かる名前が要る。`lib` 側の `fetchNews` と衝突するため、たとえば `tools: { fetchNews: fetchNewsTool }` のようにキーと変数名を分ける。
  - 影響範囲: `app/api/ai-analysis/route.ts` の 3 か所に加え、`features/ai/lib/prompts.ts` のプロンプト本文が `getNews` という名前を文字列で参照している。文字列内の参照は型チェックで見つからないので、影響範囲に必ず書く。

## 名前と中身のずれ

命名の指摘でいちばん重いのは、名前がもっともらしいのに中身と食い違っているケース。`getUserData` が実際にはネットワークリクエストを送る、`isValid` が値を書き換える、`formatX` が DB に書き込む、など。明らかに変な名前は誰でも気づくが、この種のずれはざっと読むと通ってしまい、AI が生成したコードでよく起きる。

- 名前を評価する前に、必ず関数本体を読む。名前だけ見て「良い名前」と判断しない。
- 名前が約束する動作（取得だけ、判定だけ、副作用なし、安価）と本体の動作が違えば `must` にする。
- 名前が何通りに読めるかで判断する。指摘の「理由」には、現在の名前から読み手が想像しうる誤った解釈を具体的に書く（例: 「`filterInactive` は非アクティブを残すとも除くとも読める」）。

## 誤解されやすい形

### 両義的な動詞

自作の関数で、残すのか除くのか、切り詰めるのか削除するのかが読み取れない動詞は指摘する。

- `filterX` → 残すなら `selectX` / `pickX`、除くなら `excludeX` / `omitX`
- `clipX` / `cutX` → 最大長に収めるなら `truncateX`

組み込みメソッドの `Array.prototype.filter` の呼び出しは指摘しない。JS では「条件に合うものを残す」と意味が決まっている。

### 上限・下限の定数

`LIMIT`、`THRESHOLD`、裸の数値リテラルでは、境界を含むかどうかが分からない。上限・下限には `MAX_` / `MIN_` を付け、比較演算子（`<` か `<=` か）が名前と合っているかを確認する。オフバイワンの温床なので、比較の向きと名前が食い違っていれば `must`。

```ts
// features/ai/components/agent-selector.tsx
// 点击分析师卡片：已选则取消，未选且未满 2 个则添加
} else if (selected.length < 2) {
```

ここで出すべき指摘: `2` に名前がなく、上限であることをコメントが補っている。`const MAX_SELECTED_AGENTS = 2` を定義し、`selected.length < MAX_SELECTED_AGENTS` にする。同じ上限が UI 側の文言や他の判定にも出てくるなら、それも影響範囲に書く。

### 範囲

TS/JS で一番大事な例外: `Array.prototype.slice(start, end)`、`String.prototype.substring(start, end)` など、言語の標準 API は `start` / `end` を半開区間（終点を含まない）で使っている。だから TS/JS のコードでは、半開区間の `start` / `end` は慣習どおりであり、指摘しない。C++ 流の `begin` / `end` への改名も勧めない。

指摘するのは次の場合だけ。

- 終点を含む閉区間なのに `end` / `to` と名付けている → `last` / `max`、または `endInclusive` のように明示する
- 同じコードベースで、閉区間と半開区間が同じ名前で混在している
- 日付の範囲（`from` / `to`）で、終点の日を含むかどうかを本体や呼び出し先から判断できない → 名前か JSDoc で明示するよう提案する。呼び出し先の API を確認できなければ `unverified` を付ける

### 真偽値

- 真偽値の変数・プロパティ・関数は `is` / `has` / `can` / `should` で始める（`loading` → `isLoading`）。ただしプロジェクト内で慣習が揃っているなら、その中の不統一だけを指摘する。
- 否定形の名前（`noCache`、`isNotReady`、`skipValidation`）は肯定形にできるなら提案する。特に `!isNotX` のような二重否定が呼び出し側に現れていれば `should`。
- DOM や UI ライブラリの慣習に合わせた否定形は指摘しない。`disabled`、`hidden`、`readOnly` は HTML 属性と同じ名前であり、コンポーネントの props として自然。Dialog などの `open` / `onOpenChange`、shadcn/ui の `hideLabel` のようなライブラリ側の API と、それに合わせた state 名（`const [open, setOpen]`）も対象外。

### 期待されるコスト

`get` 以外にも、読み手がコストを思い込む名前がある。`size` / `length` / `count` は O(1) で副作用なし、TS の `get` アクセサはフィールド読み出し程度、と思われる。

- アクセサの構文（`get foo()`）自体は指摘しない。ただし、アクセサの中でネットワーク通信・DB アクセス・全件走査をしているなら、メソッドに変えて動詞でコストを示すよう指摘する。
- `count` / `size` という名前の関数が全件を取得して数えているなら指摘する。

## 改名を適用するとき

レポートだけでなく、ユーザーに修正を頼まれて改名を適用する場合は、先に影響範囲（その名前を参照している箇所）を grep で数える。

- 参照が同じファイルの中だけなら、そのまま適用してよい。
- 他のファイルの参照も書き換える必要がある場合は、適用する前に必ずユーザーに確認する。確認では、変更が必要なファイルと箇所の数、文字列で参照している箇所（プロンプト、設定、ドキュメント）の有無を示し、「これらも一緒に変更してよいか」を聞く。確認が取れるまで、他のファイルは触らない。
- 確認が取れない間は、改名案をレポートに書くだけにとどめる。

## プロジェクト規約への格上げ

同じ種類の命名の指摘が 3 件以上出たら、個別の改名に加えて、プロジェクトの規約（`CLAUDE.md` や ESLint の命名ルール）に書くことをレポートの末尾で 1 行だけ提案する。AI に毎回「読み手の立場で考えて」と頼むより、ルールとして書いておくほうが確実に守られる。規約ファイル自体は編集しない。

## その他のチェック

- **汎用的な名前**（`tmp`、`data`、`result`、`info`、`retval`）: 変数のスコープが数行を超える場合や、具体的なものを保持している場合だけ指摘する。3 行の swap での `tmp` は問題ない。
- **金額の名詞が実体と違う**: `cost`（支払った額）、`proceeds` / `revenue`（受け取った額）、`amount` / `total`（符号なしの合計）、`value`（評価額）は別の概念。売却で受け取った金額を `sellCost` と呼ぶ、取得原価を `value` と呼ぶ、といった食い違いは、式（`buyCost - sellCost`）が合っていても読み手に換算を強いる。式の符号と、その語が指す方向（支払いか受け取りか）が合っているかを見る。同じコードベースで同じ概念に別の語が混在していれば、名前の統一を提案する
- **単位がない**: 時間・サイズ・金額を表す数値には単位を付ける — `timeoutMs`、`maxSizeBytes`、`priceJpy`。
- **注意が必要な属性がない**: 扱いに注意すべき値はそれを名前で示す — `rawHtml` / `unsafeHtml`（対になるのは `sanitizedHtml`）、`plaintextPassword`。
- **長さとスコープ**: ごく狭いスコープなら短い名前でよい（1 行のコールバックでの `i`、`x`）。export される名前やモジュールレベルの名前には十分な情報を持たせる。
- **略語**: チームの新メンバーが読んで分かるもの（`id`、`url`、`db`）だけを許す。プロジェクト内だけで通じる略語は指摘する。
- **同じ概念に別の名前**（または同じ名前に別の概念）: 同じコードベース内で混在していれば指摘する。

## 指摘しないもの

- フレームワークやライブラリが要求する名前（React の `useX`、Next.js の `getServerSideProps`、ORM のメソッド名）
- 命名の大文字小文字規則（camelCase など） — ESLint に任せる
- 影響範囲が大きい改名（公開 API、呼び出し元が多い）を、影響範囲を書かずに提案すること。その場合は影響範囲を列挙し、重要度を `should` に下げる。
