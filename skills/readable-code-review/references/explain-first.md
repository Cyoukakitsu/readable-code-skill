# 説明と構造の対応

原則: コードは機械への命令であると同時に、読み手への思考の記録でもある。書く前に解決方法を自然言語で説明し、コードの構造をその説明と一対一で対応させる。説明の順序とコードの順序が大きくずれているなら、ロジックが遠回りしているか、ネストが深いか、複数のステップが混ざっている。（第 12 章）

## レビューのやり方: 説明してから比べる

1. 対象の関数（`useEffect` の本体、Route Handler を含む）を読み、まず自分で「何をどの順序で行うか」を 1〜3 文、3〜5 ステップで説明する。
2. その説明とコードの並びを比べ、次のずれを探す。
   - 説明に出てこないのに、場所を取っている処理（下位問題、役目を終えた処理、重複）
   - 説明の順序と、コードの順序が違う
   - 説明では 1 ステップなのに、コードの複数の場所に散らばっている。逆に、1 つのかたまりに複数のステップが混ざっている
   - 5 ステップ以内に収まらない（階層が足りない）
3. 要件や設計の資料（Issue、PR の説明、仕様書）がレビュー対象に含まれていれば、自分の説明の代わりにそれを使う。ない場合、コードから逆算した説明は、要件が正しいことの裏付けにならない（[comments.md](comments.md) の「AI が書いたコメントについて」と同じ）。

設計のステップを先に決めて実装を AI に任せている場合、最初に確かめるのは、設計のステップ列がコードの構造に一対一で出ているか。4 つのステップが 1 つのループに詰め込まれていたら、設計どおりに書かれていない。[single-task.md](single-task.md) として指摘する。

重要度: 説明に出てこない副作用（保存、送信、外部の呼び出し）が混ざっていて、関数名や呼び出し元から予測できないなら `must`。そのほかのずれは `should`、細かいものは `optional`。

## 上位の流れを 3〜5 ステップに保つ

おおむね 30 行を超える関数で、細部（ループ、条件、整形）が流れを隠しているものは、メインの関数をステップの呼び出しだけにし、細部を下の層の関数へ下ろすよう提案する（`should`）。各ステップが一文で言える大きさになるまで、同じ手法を繰り返して適用する。

- ステップ関数の名前は、説明の一文になっていること。`step1`、`processData` のような名前は勧めない（[naming.md](naming.md)）。
- 切り出しは動作を変えない。修正案を出す前に、次を確かめる。
  - 非同期のステップに `await` が付いているか（付け忘れると、Promise が捨てられて、エラーが握りつぶされ、順序も崩れる）
  - 例外を投げる場所と、呼び出し側で受け取る場所が変わっていないか
  - 切り出しで渡す引数が 4 つ以上になるなら、分け方が悪い。そのときは提案しない
- 切り出しすぎとの線引きは [extraction.md](extraction.md) と同じ。基準は「呼び出し側を読むとき、切り出した関数の中に入らずに済むか」。一度しか呼ばれなくても、メインの流れの一文になるなら価値がある。中身が 1、2 行で、名前がその言い換えにすぎないなら価値がない。

## 条件の並びを説明の順に

「すべて成り立つときだけ `true`」をネストで書いたものは、「〜なら不可」の列（ガード節）に直すと、説明の順序と対応する。ネストの段数の基準は [control-flow.md](control-flow.md) に従う（4 段を超えたら `should`）。4 段に満たなくても、各条件が互いに独立した除外条件で、ガード節にしたほうが明らかに読みやすいなら `optional` で提案してよい。

- 条件を反転するときは、境界値の取り違えが起きやすい（`< 18` を反転すると `>= 18`）。修正案を出す前に、境界ちょうどの値（18 歳ちょうど、期限ちょうど）で元のコードと結果が同じになることを確かめる。
- 条件が互いに依存している、または分岐の両側に処理がある場合は、無理にガード節にしない。

## 標準ライブラリを知る

置き換えを勧める判断は [extraction.md](extraction.md) の「自作する前に、すでにあるものを探す」に従う。ここでは、向きの注意だけを足す。

- 置き換えの価値は、標準の API が意図を名前で語れること（`some`、`find`、`at`、`Intl`、`URLSearchParams`、`structuredClone`）。手書きの `for...of` が読みやすく、動作も同じなら、`reduce` への置き換えは勧めない。特に、カテゴリ別の件数のようにオブジェクトを組み立てる処理は、`reduce` より `for...of` のほうが読みやすい（[compression.md](compression.md)）。
- TS では、`reduce` の初期値に `{}` を渡すと `acc` の型が `{}` になり、`acc[item.category]` が型エラーになる（`strict` で確認済み）。`reduce` を勧めるなら、型引数を明示するか、そもそも `for...of` のままにする。
- 標準の API が使えるかは、実行環境と `tsconfig` の `lib` を確かめてから提案する。確かめられなければ `unverified`。

## 指摘しない

- 説明すると 1 文で済む短い関数。ステップに分けなくてよい
- 流れが一本で、5 ステップ以内、各ステップが数行のもの
- フレームワークが形を決めている構造（`useEffect` が返すクリーンアップ関数、Route Handler の入口など）
- 説明の順序とコードの順序が一致しているもの

### 例（作者自身のプロジェクトより）

```ts
// features/assets/lib/date-utils.ts（getFromDate）— 指摘しない部分
if (range === "YTD") {
  return `${now.getFullYear()}-01-01`;
}

if (range === "MAX") {
  return firstTransactionDate ?? "2020-01-01";
}

const daysMap: Record<Range, number> = { ... };
```

「YTD なら年初、MAX なら最初の取引日、それ以外は日数をさかのぼる」という説明と、コードの並びが一致している。ガード節の形も説明どおりで、構造は直す必要はない（`firstTransactionDate` を呼び出し元が渡していない問題は、構造ではなく [less-code.md](less-code.md) の指摘として出す）。

一方で、この関数の `daysMap` には `YTD: 0` と `MAX: 0` があるが、どちらもその前の `return` で到達しない。説明に出てこない要素で、`Record<Range, number>` が全キーを要求するために入っているだけである。`"1M" | "6M" | "1Y"` だけの型にすれば消せる（`optional`）。

```ts
// features/assets/hooks/use-portfolio-candlestick-chart.ts（useEffect の冒頭）
if (chartRef.current) {
  chartRef.current.remove();
  chartRef.current = null;
  seriesRef.current = null;
}
```

この `useEffect` を説明すると「チャートを作り、表示モードに応じた系列を載せ、サイズの変化に追従させ、片付ける」になる。冒頭の「古いチャートを破棄する」は、説明に出てこない。このファイルでは `chartRef` に代入しているのは effect の中だけで、クリーンアップ（末尾の `return`）が毎回 `chartRef.current = null` にするので、冒頭のこの分岐は実行されない（`unverified`: 他のファイルから `chartRef` を書き換えていないこと）。役目を終えた処理として削除を提案する（`should`、[defensive-code.md](defensive-code.md) と同じ行範囲なので 1 件にまとめる）。
